# Rung 阶段 N 报告:<一句话说清这一阶段做了什么>

作者:Roddy Huang · 日期:YYYY-MM-DD · **上限 4 页**

> 页数上限是特性不是限制。它逼你选择说什么 —— 而选择本身就是这份报告要训练的东西。
> 写不下就说明你还没想清楚哪部分最重要。

---

## 1. 引言

三段以内,回答:

- 这一阶段的**系统目标**是什么(要让订单簿多做到哪件事)
- 你实现了**哪几个版本**,它们的区别在哪一个点上
- 结论先说:哪个版本赢了,赢多少

> 好的引言让人读完就知道整份报告的结论。悬念留给小说。

---

## 2. 实现

### 2.1 版本 A:<名字>

用**伪代码或散文**描述算法,不要贴大段源码 —— 源码在仓库里,报告里贴一遍是浪费页数。
只在某一行确实是关键时才贴那一行。

说清:
- 用了什么数据结构,为什么
- 关键操作走的是哪条路径

### 2.2 版本 B:<名字>

同上。

### 2.3 两者的区别

**只有一个点不同**,是哪个点?

如果你发现有两个以上的点不同,那这次对比是不干净的 —— 测出来的差异
没法归因到任何一个具体的改动上。回去把变量控制成一个。

### 3.2 随机测试与参考模型

- 用什么生成随机订单流,种子是多少(必须固定,否则不可复现)

## 4. 复杂度分析

| 操作 | 版本 A | 版本 B | 关键操作是什么 | 依据 |
|---|---|---|---|---|
| `insert` | O(?) | O(?) | | |
| `cancel` | O(?) | O(?) | | |
| `best` | O(?) | O(?) | | |
| `submit` | O(?) | O(?) | | |
| `depth` | O(?) | O(?) | | |

**N 指什么**要说清(簿上挂单总数?档位数?单档位深度?这三个不是一回事)。

分析时说明你算的是哪种情况:

- **最坏情况** —— 例如 `cancel` 撤的是队尾那笔
- **平均情况** —— 例如 `cancel` 的 id 在簿上均匀分布
- **摊还** —— 例如连续 N 次 `insert` 的每次平均成本

不需要严格证明,但要说清你的假设。

## 5. 定量评估

### 5.1 测量方法

- 命令:`./scripts/eval.sh`
- 机器:<CPU / 内存 / OS>
- build:release(**必须**,debug 数字无意义)
- 每个数据点跑了几次,取的是平均还是中位数

### 5.2 数据

按**订单流模式**分表。每张表一个模式。

**模式:`<insert-only / high-cross / cancel-heavy>`**

| n | 版本 A (ns/op) | 版本 B (ns/op) | 加速比 |
|---|---|---|---|
| 100 | | | ×  |
| 200 | | | ×  |
| 500 | | | ×  |
| 1000 | | | ×  |
| 2000 | | | ×  |

**加速比那一列是这份报告的核心。** 它把「A 比 B 好」变成一个可以被质疑的数字。

### 5.3 图

至少一张:x 轴规模,y 轴 ns/op,每个版本一条线,按模式分组或分图。

图要能黑白打印看清:不同的点型(圆/方/三角),不要只靠颜色区分。

### 5.4 理论与实测是否吻合

拿 §4 的 big-O 和 §5.2 的数据对照:

- 如果分析说 O(1),实测曲线应该是平的
- 如果说 O(N),应该是直线
- 如果说 O(N²),应该是抛物线

**不吻合的地方要解释。** 常见原因:常数因子太大、缓存效应、
规模还不够大所以低阶项占主导、或者 —— 你的分析错了。

> 「不吻合但我不知道为什么」是一个合法的结论,比强行编一个理由好。
> 把它记下来,后面阶段可能会自己解释。

## 6. 结论

三段以内:

- **哪个版本赢了,在什么条件下赢** —— 条件很重要,可能在某个模式下反而输
- **代价是什么** —— 赢的那个在哪个维度上付了钱(代码量?可读性?内存?)
- **下一步的瓶颈在哪** —— 这一阶段做完之后,最慢的还是什么
