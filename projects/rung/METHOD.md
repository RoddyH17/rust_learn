# 系统设计怎么想:七条方法

> [`PRIMER.md`](PRIMER.md) 讲**思考的对象**(交易所和流动性),这一篇讲**怎么思考**。
>
> `stages/stage-00.md` 全是问题没有方法 —— 这一篇补上。读完再回去做 stage-00。

---

## 为什么 stage-00 只给问题

因为**架构能力不是知识,是提问的顺序**。

同一个系统,两个人都能写出来。差别在于:一个人是「先想到 HashMap,然后把问题塞进 HashMap」,
另一个人是「先搞清楚谁在问什么,然后发现答案恰好是 HashMap」。

两份代码可能一模一样。但第二个人能回答「如果需求变成 X,这里要改成什么」,第一个人不能。

下面七条方法,就是那个提问的顺序。

**每一条我都会用同一个例子走一遍:你自己的 `rust_learn` 笔记管道。**
选它是因为你最熟(每天都在用),而且它和订单簿完全无关 —— 不会剧透 stage-00 的答案。

### 工作示例的对象

```
  Notion (System III)          ← 学习材料的源头
        │  notion.sh fetch
        ▼
  .cache/notion/*.md           ← 落盘缓存
        │
        │  你看视频、写代码
        ▼
  dayN/<crate>/src/main.rs     ← 现场记录(编号小节)
        │              └──▶ examples/practice.rs   ← 练习
        │
        ├──▶ dayN/NOTES.md      ← 技术细节的唯一来源
        │
        │  notion.sh render N
        ├──▶ Notion 日页
        │
        └──▶ ~/blog/.../day-N-*.mdx   ← 只写叙事
```

## 方法一 · 从问题清单出发,不从数据结构出发

**反模式**:「这是个订单簿 → 订单簿是个映射 → 用 HashMap」。
这叫**从工具出发**。工具选对了是运气,选错了你不知道为什么错。

**正确顺序**:

```
1. 谁会用这个系统?列出所有角色
2. 每个角色会问它什么问题?
3. 每个问题问得多频繁?
4. 每个问题慢了会怎样?
5. ——到这里,数据结构基本已经被逼出来了——
6. 现在才去挑容器
```

### 工作示例

对笔记管道问这五步:

| 角色 | 问题 | 频率 | 慢了会怎样 |
|---|---|---|---|
| 你(学习时) | 「今天该学什么?」 | 每天 1 次 | 无所谓 |
| 你(写笔记时) | 「昨天我踩了什么错?」 | 每天 1 次 | 无所谓 |
| `render` | 「dayN 的现场记录里有哪些小节?」 | 每天 1 次 | 无所谓 |
| `audit` | 「哪些天的下游没跟上?」 | 每周 1 次 | 无所谓 |
| **Claude** | **「System III 里 dayN 那页写了什么?」** | **每次对话多次** | **每次都进上下文,成本随页面增长** |

最后一行的频率**高出两个数量级**,而且它的代价不是「慢」,是「贵」——
MCP 每次取数都会把整页塞进上下文,System III 曾经 50K 字符 ≈ 15-20K token,且逐日增长。

**于是设计被逼出来了**:落盘缓存 + 按天切片。这样只读需要的那一页,成本不随页面总量增长。

注意这个推导过程里,**没有任何一步是在比较技术方案**。是问题清单自己选出了答案。

> **对应 stage-00**:T0.3(问题清单 + 调用频率)就是这一条。它是阶段 0 里最重要的一题。

## 方法二 · 频率决定成本分配,直觉会骗你

性能**不是均匀的**。为一天问三次的操作做优化是纯粹的浪费。

但人的直觉按「这件事**重不重要**」分配注意力,而不是按「问得**多频繁**」。
这两者经常不一致,而且不一致的地方就是你会犯错的地方。

### 工作示例

「把笔记推到 Notion」这件事**很重要** —— 它是整条管线的产出。
但它一天只跑一次。所以 `render` 用 Python 正则切分字符串、性能烂到爆,**完全无所谓**。

反过来,「Claude 读某一天的笔记」这件事听起来**很琐碎**,但它一天发生几十次。
所以它值得为它专门做一个缓存层、一个切片命令、一套 diff 机制。

**判断题**:如果你只有一天时间做优化,你会优化哪个?
按重要性选,你会去优化 render;按频率选,你会去做缓存。**后者是对的。**

> **对应 stage-00**:T0.3 的 Q4 ——「有没有哪一条你觉得很重要,但其实一天才问几次?」

## 方法三 · 边界的判据是「要不要硬」

系统要拆成几块?这个问题人人都会问。真正的问题是下一个:

> **拆开之后,这条边界靠什么保证不被破坏?**

Rust 给你三种强度的边界,强度递增:

| 边界 | 靠什么保证 | 破坏它需要 |
|---|---|---|
| 命名约定(`_internal`) | **自觉** | 什么都不需要 |
| `mod` + `pub(crate)` | **半自觉** | 改一个可见性修饰符 |
| **不同的 crate** | **编译器** | 改 `Cargo.toml`,而且循环依赖时根本改不了 |

判据只有一条:

> **这条边界如果被破坏了,后果有多严重?严重到不能靠自觉,就拆 crate。**

### 工作示例

笔记管道里有一条边界,`notion.sh` 的注释里写得很明白:

> 这是检索层,不是结论层 —— 切片、落盘、diff 是确定性的;
> 「这一节属于哪天」「哪道题该抄进 practice.rs」需要判断,不在这里做。

**这条边界要不要硬?**

想清楚破坏它的后果:如果脚本开始做判断(比如自动决定某节属于哪天),
那么当它判断错了,你**不会知道** —— 因为它是自动的,你不会去复核。
错误会静默地流进 Notion 和博客,而且你事后无从追溯它是怎么错的。

**后果是「静默的错误」,这类后果最严重**(比崩溃严重得多,崩溃至少你知道)。
所以这条边界必须硬 —— 它被硬在了「脚本 vs 人/AI」这个层面上,比 crate 边界还硬。

### 反过来:不要过度拆分

拆开是有代价的,而且代价经常被低估:

- 编译时间变长(每个 crate 是独立编译单元)
- 改一个类型要动多个 `Cargo.toml`
- **循环依赖会让你卡死** —— 而且往往是拆完才发现
- 跨 crate 的类型没法加固有方法(阶段 5 会撞到)

**如果你说不出拆开的代价,说明你还没真正理解这次拆分。**

> **对应 stage-00**:T0.4。Q5 特意要求你列出至少两条代价 —— 列不出来就回去重想。

## 方法四 · 不变量思维

**不变量**(invariant)是:无论系统经历什么合法操作,都必须成立的性质。

它不是「测试用例」。测试用例说「输入 A 应该得到 B」;不变量说「**不管输入什么,C 都必须成立**」。

好的不变量有三个特征:

1. **可检验** —— 能写成一个返回 bool 的函数
2. **跨操作成立** —— 不是「某个函数结束时成立」,是「任何时刻从外面看都成立」
3. **违反了就是 bug** —— 没有例外,没有「这种情况下可以不成立」

### 怎么找不变量

问自己:**「什么东西,无论如何都必须是真的?」**

再问一遍:**「如果它假了,我怎么才能发现?」** ——
如果答案是「发现不了」,那这条不变量特别值钱,因为它对应的是**静默的错误**。

### 工作示例

笔记管道的不变量:

| 不变量 | 违反了会怎样 | 能自动发现吗 |
|---|---|---|
| `practice.rs` **必须原样可编译** | 你打开文件想做题,先得修编译错误 | ✅ `cargo run --example practice` |
| 每个 `dayN` 至少有一个 crate | `render` 找不到 `main.rs`,直接报错 | ✅ 脚本里检查了 |
| `main.rs` 有编号小节 | **`render` 静默产出空内容**,或者报「还是空骨架」 | ⚠️ 报错了,但 day5/5.5/6 全是零小节,没人注意 |
| NOTES 是技术细节唯一来源,博客只写叙事 | 两边内容重复,改一处忘另一处,长期分叉 | ❌ **发现不了** |

最后一条最危险 —— 它没有任何自动检查,只能靠约定。这就是为什么它被写进了 README 的显眼处:
**没法用工具保证的不变量,只能用文档反复强调。**

### 冗余数据一定要配不变量

任何时候你存了「本来可以算出来」的东西(缓存、计数、总和),你就制造了一个不变量:
**这份冗余必须和真相一致**。

缓存的经典难题不是「怎么存」,是「怎么保证它不失效」。
标准解法:**把维护点收敛到最少的几个地方,并让其它代码没有能力直接改底层数据**
(在 Rust 里就是把字段设为私有,只留几个方法)。

> **对应 stage-00**:T0.2 的 Q4「哪些状态转移是不允许的」—— 那就是不变量。
> 阶段 2 你会亲手制造第一个冗余缓存,阶段 7 会用 proptest 反复冲击所有不变量。

## 方法五 · 可逆 vs 不可逆

**架构决策 = 不可逆的那些。其余的都只是实现选择。**

判据:

> 如果三个月后要改它,**要改多少处别人的代码**?
>
> - 只改这个文件 → 可逆,快点决定,错了再改
> - 要改所有调用方 → 半可逆,想一想
> - **已经公开进 API,别人依赖了** → 不可逆,慢慢想

在 Rust 里有一个极其清晰的分界线:**`pub` 就是不可逆的开始。**

一旦某个类型/字段/方法是 `pub`,它就是一个**承诺**。改它要升大版本,要通知所有使用者。
所以写库时的默认动作应该是:**能不 `pub` 就不 `pub`**,先私有,等真的有第二个使用者了再公开。

### 工作示例

笔记管道里两个决定的对比:

| 决定 | 可逆吗 | 为什么 |
|---|---|---|
| `render` 用正则切分还是用 AST 解析 | **可逆** | 纯内部实现,换掉不影响任何人 |
| 编号小节的格式定成 `// ---------- N. 标题 ----------` | **不可逆** | 已经写进 day4 和 day7 的 17+12 个小节里了。改格式 = 改所有历史文件 |
| 博客 slug 定成 `day-N-<topic>` | **不可逆** | slug 被硬编码进了 NOTES.md 的头部链接,而且发布后 URL 不能改 |

第三条尤其典型:**它当初看起来只是个命名习惯**,但因为被别处引用了,就变成了不可逆的。
这类「不知不觉变成不可逆」的决定最危险 —— 所以 ADR 的「何时推翻」那一段才重要:
它逼你在决定的当下就想清楚这东西的可逆性。

> **对应 stage-00**:整个 T0.4;以及阶段 10 的收尾追问。

## 方法六 · 代价必须能说出来

**每一个技术选择都在某个维度上付了钱。找不到那个维度,只说明你还没看见它。**

如果你说「我选 A,因为 A 更好」,那你没在做决定,你在陈述偏好。
真正的决定长这样:「我选 A,代价是 X 变差了,我接受,因为当前 Y 比 X 重要」。

常见的代价维度,挨个过一遍:

- 代码量 / 可读性 / 新人上手成本
- 编译时间 / 二进制体积
- 内存占用 / 缓存局部性
- **未来改动的自由度**(方法五)
- **出错时的排查难度**:编译期错误 → 运行时 panic → 静默错误,一个比一个糟

最后一条值得展开。Rust 的很多设计取舍,本质上是在这三档之间移动:

| | 错误何时暴露 | 例子 |
|---|---|---|
| 最好 | **编译期** | 类型不匹配、忘了处理 `None` |
| 其次 | **运行时 panic** | 数组越界、`unwrap()` 空值、`RefCell` 借用冲突 |
| 最糟 | **静默错误** | 缓存和真相不一致、忘了写 `.or_insert()` 的 `entry()` |

你在 day7 踩过第三档那个坑(`entry()` 只写一半,编译过、不报警、什么都不做)。
那次的教训用一句话说就是:**把错误往上一档推,是值得付代价的。**

> **对应**:ADR 模板的「代价」段。没有代价 = 没想清楚。

## 方法七 · 先痛,再给药

**在你亲手写出重复代码之前,不要用抽象消除它。**

原因很直接:抽象是有成本的(多一层间接、报错信息变长、新人要多理解一个概念)。
只有当你**看见**了它消除的痛苦有多大,你才能判断这个成本值不值。

推论,也是一条很实用的规矩:

> **什么时候该提取抽象?出现第二个调用者时,不是第一个。**

一个调用者时提取的抽象,几乎必然是错的 —— 因为你是在猜第二个调用者长什么样。
等第二个真的出现了,你有两个样本,抽象才有依据。

### 工作示例

`new_day.sh` 是从「连续手工建了三天目录之后」才写的,不是第一天就写的。
如果第一天就写脚手架,你不会知道要生成 `.vscode/launch.json` 的两条配置 ——
那是手工做到第三天才觉得烦的。

同理,`NOTES_TEMPLATE.md` 的六个固定小节,是写了几天笔记之后**从已有笔记里归纳出来的**,
不是先设计模板再往里填。

> **对应 stage-00 / 阶段 3**:阶段 3 硬性要求你**先写两份重复的代码**,对照数出重复行数,
> 才允许合并成泛型。顺序不许调换。

## 最后:一个反面清单

以下这些话如果出现在你的思考里,停下来 ——

| 说法 | 问题在哪 | 换成 |
|---|---|---|
| 「这个用 HashMap 就行」 | 从工具出发(违反方法一) | 「最频繁的操作是什么?」 |
| 「A 比 B 更好」 | 没说代价(违反方法六) | 「A 的代价是 X,我接受因为 Y」 |
| 「先加个 `pub`,以后再说」 | `pub` 是不可逆的(违反方法五) | 「先私有,等第二个使用者出现」 |
| 「这里可能会慢」 | 没量化 | 「n 到多少时它会超过 X 微秒」 |
| 「顺手抽象一下」 | 只有一个调用者(违反方法七) | 「等第二个调用者出现」 |
| 「应该不会出这种情况」 | 这正是不变量该管的(违反方法四) | 「写成断言,让 proptest 去撞」 |
