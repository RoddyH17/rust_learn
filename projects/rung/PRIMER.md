## 0. 一句话说清这一篇要回答什么

> **为什么订单簿长成那个样子?**

答案不在算法书里。它在「谁在用它、他们在问什么问题、问得多频繁、慢了会损失多少钱」里。
所以我们得先把这些人和这些钱讲清楚。

## 1. 从两个人想做交易开始

小 A 有 100 股股票想卖,小 B 想买 100 股。他们怎么成交?

**方案一:直接谈。** 小 A 满世界找想买的人,谈价格,成交。
问题很明显:找人要时间,而且小 A 不知道市场上「合理价格」是多少 —— 他可能卖便宜了,也可能一直卖不掉。

**方案二:找个固定的集合点。** 所有想买想卖的人都到这里来,把自己的意愿挂出来。
这个集合点就是**交易所**。

到这里,一个关键的观念转变发生了:

> 交易所卖的**不是撮合服务**,是**流动性**。

撮合本身是个很简单的算法。人们愿意去某个交易所,是因为那里**有对手方** ——
你想卖,立刻就有人买;你想买大额,不用把价格推高很多。这个「立刻有对手方」的性质,就叫流动性。

---

## 2. 流动性到底是什么

流动性不是一个数字,是**三个维度**:

| 维度 | 英文 | 通俗说法 | 怎么量 |
|---|---|---|---|
| **紧度** | tightness | 买价和卖价离得有多近 | **买卖价差**(spread) |
| **深度** | depth | 每个价位上有多少量 | 各档位挂单量 |
| **弹性** | resiliency | 被大单打乱之后,多快恢复 | 恢复时间 |

举个具体的:

```
        卖盘(ask)                        ← 别人愿意卖给你的价
        10.52  ×  300 股
        10.51  ×  500 股
        10.50  ×  200 股   ← 最优卖价(best ask),你想买,得付这个价
    ────────────────────   ← 买卖价差 spread = 10.50 - 10.49 = 0.01
        10.49  ×  400 股   ← 最优买价(best bid),你想卖,只能拿这个价
        10.48  ×  600 股
        10.47  ×  250 股
        买盘(bid)                        ← 别人愿意从你手里买的价
```

这张图就是**订单簿**(order book)。它是流动性的具体形态。

看懂三件事:

1. **买价永远低于卖价。** 如果有人愿意 10.50 买、有人愿意 10.50 卖,他们当场就成交了 ——
   所以还挂在簿上的,一定是没成交的,一定是 `best_bid < best_ask`。
   **这是订单簿最重要的不变量**,你在阶段 5 会把它写成一行断言。
2. **价差就是你的交易成本。** 你买进付 10.50,立刻卖出只能拿 10.49 —— 一进一出就亏 0.01。
   价差越小,流动性越好,交易成本越低。
3. **价格是离散的。** 图上没有 10.495。最小的价格变动单位叫 **tick size**(这里是 0.01)。
   所有交易所都规定 tick size —— 否则会有人挂 10.4999999 来插队,而这种「插队」对市场毫无意义。

> **⚠️ 这一条会直接影响你的类型设计。** 价格不是连续的实数,是「多少个 tick」。
> 但具体在 Rust 里怎么表达,是你在 stage-00 的 T0.5 要自己回答的,这里不给答案。

## 3. 两种订单,两种角色

| | 限价单 Limit Order | 市价单 Market Order |
|---|---|---|
| 你说什么 | 「10.49 买 100 股,不到这个价我不买」 | 「买 100 股,多少钱都行」 |
| 结果 | 可能立刻成交,也可能挂在簿上等 | 立刻成交,价格由簿上现有的挂单决定 |
| 你对流动性做了什么 | **提供**了流动性 | **消耗**了流动性 |

由此产生两个角色:

- **Maker(做市方)**:挂单等待成交的人。他**提供**流动性 —— 是他让簿子上有东西。
- **Taker(吃单方)**:主动吃掉现有挂单的人。他**消耗**流动性。

**成交价按 maker 的价格。**

为什么?想清楚这一条,你就懂了交易所规则设计的底层逻辑:

> maker 先把报价挂出来,承诺「我愿意 10.50 卖」。
> taker 后来,接受了这个承诺。既然是接受一个既有的承诺,当然按承诺的价格算。
>
> 反过来会怎样?如果按 taker 报的价成交,那 taker 只要报一个离谱的价(比如 999),
> 就能把 maker 的挂单以 999 吃掉。**没人敢挂单了,流动性直接归零。**

所以「成交价按 maker」不是一条随便定的规则,它是**让人敢挂单的前提**。

大部分交易所还会给 maker **更低的手续费**(甚至返佣),因为交易所要买流动性。

## 4. 撮合规则:价格优先,时间优先

两笔买单都想买,谁先成交?

**第一优先级:价格。** 出价高的先成交(买方),要价低的先成交(卖方)。
这很自然 —— 出价高的人更「想要」,他应该排前面。

**第二优先级:时间。** 同一个价格上,**先挂的先成交**。

第二条为什么是时间,而不是「量大的先成交」或者「随机」?

> 因为要**奖励先报价的人**。
>
> 第一个在 10.50 挂卖单的人,承担了最大的风险 —— 他不知道市场接下来往哪走。
> 后面跟着挂的人是在搭便车。如果不给先来者排队优势,就没人愿意第一个报价,
> 而没有第一个报价,簿子就是空的。

这两条规则合起来叫 **price-time priority**(价格-时间优先)。

> **⚠️ 「时间优先」意味着同一价格上的订单之间有严格顺序,先进的先出。**
> 这直接约束了档位内部的数据结构 —— 但具体用什么容器,还是 T0.5 你自己答。

**排队位置(queue position)有实际价值。** 你排在 10.50 这一档的第 1 位还是第 50 位,
决定了你成交的概率完全不同。专业做市商会为了保住队列位置而不轻易撤改单 ——
这也是为什么「改价格 = 撤单 + 重新挂,失去排队位置」这条规则很重要。

## 5. 做市商:流动性是从哪来的

簿子上那些挂单不是散户挂的 —— 绝大部分来自**做市商**(market maker)。

**做市商的商业模式**:同时在买卖两边挂单,赚价差。

```
挂买单 10.49  ←── 有人卖给我,我付 10.49
挂卖单 10.50  ←── 有人从我这买,我收 10.50
                   一来一回赚 0.01
```

听起来是白捡钱。但做市商要承担两种风险,这两种风险**塑造了整个系统的设计**:

### 风险一:库存风险(inventory risk)

如果只有人卖给你、没人从你这买,你手上会积累越来越多的货。
万一价格下跌,这些货就是亏损。所以做市商必须**盯着自己的库存调整报价** ——
货多了就把两边的报价都往下挪,鼓励别人来买、劝退别人来卖。

> **这解释了为什么做市商要极其频繁地改报价。** 库存每变一次,理论最优报价就变一次。
> 高频做市商每秒改报价成千上万次。

### 风险二:逆向选择(adverse selection)

这个更致命。

想象你在 10.50 挂了卖单。什么时候会有人来吃掉它?

- 情况 A:一个散户刚好想买,随手吃掉了。你赚 0.01,很好。
- 情况 B:某个人**知道**这只股票马上要涨到 11.00,所以来把你 10.50 的货全吃走。
  你「赚」了 0.01,但你卖掉的东西下一秒值 11.00 —— 你亏了 0.50。

**做市商最怕的不是价格波动,是和「比自己知道得多的人」成交。** 这叫逆向选择。

> **这解释了为什么延迟这么重要。** 如果你的报价比市场慢 1 毫秒,那 1 毫秒里所有来吃你单的人,
> 都是因为他们已经看到了你还没看到的信息。你会被系统性地挑走。
>
> 高频交易的「军备竞赛」表面上是在抢速度,本质上是**在躲逆向选择**。

## 6. 中心化交易所(CEX)的系统架构

现在你知道用户是谁了,来看系统长什么样:

```
   客户端
     │  下单
     ▼
  ┌────────┐   ┌────────┐   ┌──────────┐   ┌────────┐   ┌────────┐
  │  网关  │──▶│  风控  │──▶│  撮合引擎 │──▶│  清算  │   │ 行情发布│
  │ gateway│   │  risk  │   │ matching │   │settle  │   │  feed  │
  └────────┘   └────────┘   └──────────┘   └────────┘   └────────┘
   接入/鉴权     余额/限额      订单簿在这里     账本更新      推给所有人
   打时间戳     自成交防范     ★ 单线程 ★
   序列号
```

**几个设计上的硬约束,都能从上面的领域知识推出来:**

### 撮合引擎必须单线程

这是最反直觉、也最重要的一条。现代服务器有几十个核,为什么撮合只用一个?

因为**公平性要求确定性**。「价格优先、时间优先」这条规则,要求所有订单有一个**全局唯一的顺序**。
如果两个线程同时处理两笔订单,谁先谁后取决于操作系统调度 —— 那「时间优先」就成了「运气优先」。
交易所会被告的。

所以架构是:**多线程做接入和解析(可以并行),单线程做撮合(必须串行)**。
撮合线程唯一要做的事就是快 —— 它不做 I/O、不打日志、不分配内存。

> **这直接决定了 `rung-core` 和 `rung-match` 的形状**:零 I/O、无锁、不读系统时钟。

### 序列号,不是时间戳

「时间优先」听起来该用时间戳,但实际上用的是**单调递增的序列号**。

为什么?因为时间戳有两个问题:两台机器的时钟不可能完全同步;同一微秒内可能来多笔订单。
序列号没有这些问题 —— 它由网关统一分配,严格递增,天然唯一。

> **这也是回测能复现的前提。** 用时间戳的话,同一批订单跑两次结果会不同。用序列号,永远一样。

### 行情推送:快照 + 增量

订单簿每秒变化几十万次。不可能每次都把整本簿子推给所有人 ——
所以是「先发一个完整快照,之后只发变化量(增量)」,每条增量带序列号。
客户端发现序列号断了,就知道丢包了,要重新拉快照。

> 这一段是 S2 `rung-feed` 的核心难题。现在知道有这回事就够了。

## 7. 去中心化交易所(DEX):同样的问题,完全不同的约束

现在把上面那套搬到区块链上。**问题没变(还是要撮合、还是要流动性),但约束全变了:**

| 约束 | 中心化交易所 | 区块链 |
|---|---|---|
| 一次操作的成本 | 几乎为零 | **要付 gas 费** |
| 状态更新速度 | 微秒级 | 区块时间(以太坊 12 秒,Solana 亚秒级) |
| 谁能看到你的意图 | 只有交易所 | **所有人**(交易进 mempool 后公开可见) |
| 谁在执行 | 交易所的服务器 | 全网每个节点都要重算一遍 |

### 为什么早期链上做不了订单簿

回想第 5 节:**做市商每秒要改上千次报价**。

在以太坊上,每次挂单和撤单都是一笔交易,都要付 gas,都要等 12 秒确认。
做市商一天的 gas 费会超过他一年的利润。**订单簿模式在早期链上是经济上不可行的**,
不是技术做不到,是没人付得起。

### AMM:用一个公式代替订单簿

于是有了**自动做市商**(Automated Market Maker, AMM)。核心思路极其大胆:

> **不要订单簿了。用一个数学公式来定价。**

最经典的是**恒定乘积**(Uniswap V2):

```
        x × y = k

  x = 池子里 A 代币的数量
  y = 池子里 B 代币的数量
  k = 常数,交易前后必须相等
```

你想用 A 换 B?往池子里放 A(x 变大),池子按公式吐给你相应的 B(y 变小),保证 x×y 不变。

**这个设计的天才之处**:

- 不需要对手方。你随时能交易,对手是那个池子。
- 不需要做市商盯盘。任何人可以把资金存进池子当**流动性提供者**(LP),被动赚手续费。
- 链上只需要存两个数字,一次交易只改这两个数 —— gas 便宜。

**代价也很直接**:

| 概念 | AMM 里叫什么 | 对应订单簿里的什么 |
|---|---|---|
| 交易量大了价格变差 | **滑点**(slippage) | 吃穿多个档位 |
| LP 被套利者薅走的钱 | **无常损失 / LVR** | **逆向选择** |
| 资金利用效率 | 大部分钱躺在用不到的价位 | 深度分布 |

**关于 LVR,值得单独说一句。**
早期大家用「无常损失」(impermanent loss)描述 LP 的亏损,但它有个缺陷:
如果价格涨上去又跌回来,无常损失算出来是零 —— 可这中间套利者已经反复薅了很多次。

2022 年 Columbia 的研究者提出了更严谨的框架 **LVR**(loss-versus-rebalancing,读作 "lever"):
AMM 的价格永远滞后于中心化交易所,这个滞后每时每刻都在给套利者送钱。
**LVR 本质上就是 AMM 版的逆向选择** —— 和第 5 节做市商怕的是同一件事,
只不过 AMM 是个傻子做市商,它不会躲。

### 集中流动性:把钱放在有用的地方

Uniswap V3 的改进:LP 可以指定「我只在 1800–2200 这个价格区间提供流动性」。
资金不再摊薄到 0 到无穷大,资本效率提高几十倍。

代价是 LP 变成了主动管理 —— 价格跑出区间就不赚手续费了,得调仓。
于是又出现了帮人自动调仓的协议(Uniswap v4 的 hook 机制、Bunni 等)。

> 注意一件有趣的事:V3 把价格区间切成**离散的 tick** ——
> 这和第 2 节讲的交易所 tick size 是**同一个概念**。
> 连续的价格没法做索引,必须离散化,不管你在链上还是链下。

### 链上订单簿的回归(2026 的现状)

高性能链出现后,订单簿又回来了,而且**在永续合约上已经压过 AMM**:

| | Hyperliquid | dYdX v4 | Uniswap 类 AMM |
|---|---|---|---|
| 模式 | **链上 CLOB**,自建 L1 | **链下撮合 + 链上结算**,Cosmos 应用链 | AMM |
| 吞吐 | 约 20 万笔订单/秒 | — | — |
| 日均量(2026-04) | $5B+ | $100–300M | — |
| 权衡 | 吞吐高、订单簿全透明 | 应用链成熟、验证者更去中心化 | 被动 LP 友好,大额成交差 |

原因正是第 3、4 节讲的:**紧的永续市场需要价格-时间优先和部分成交,而 AMM 在大额上处理得很差。**

也就是说 —— **你现在要写的这个订单簿,不是「传统金融的老东西」,它是 2026 年链上交易的主流形态。**

## 8. 流动性问题如何决定系统设计 ★

这一节是全篇的落点。把前面的每一条领域事实,翻译成一条**系统约束**:

| 领域事实 | 系统约束 | 落到哪个阶段 |
|---|---|---|
| 每来一笔订单都要判断「能不能成交」→ 要知道最优价 | **「最优价是多少」是被问得最频繁的问题**,它决定容器选型 | 阶段 3 |
| 价格是离散的 tick,不是连续实数 | 价格要能精确比较、能当索引的 key | 阶段 1、3 |
| 价格优先、时间优先 | 档位之间要**有序**,档位内部要**保序** | 阶段 2、3 |
| 做市商每秒改上千次报价 | **撤单必须极快**,不能是「遍历找它在哪」 | 阶段 4 |
| 改价 = 撤 + 重挂(失去队列位置) | 撤单要能把订单**还给**调用方,而不只是返回成功/失败 | 阶段 4、6 |
| 逆向选择 → 延迟军备竞赛 | 热路径不许有 I/O、不许有意外的内存分配 | 阶段 8 |
| 公平性要求确定性 | 单线程;不读系统时钟;不依赖哈希表迭代顺序 | 阶段 9 |
| 买价永远低于卖价 | 一条**必须永远成立**的不变量,可以写成断言反复冲击 | 阶段 5、7 |
| 交易所要能重放事故、回测策略 | 同一份事件日志重放两次,结果必须逐字节相同 | 阶段 9 |
| 链上的瓶颈是 gas 和状态大小,不是撮合速度 | DEX 和 CEX 的架构会在同一个内核之上分岔 | S2 之后 |

**这张表就是本篇的全部意义。**

数据结构不是从算法书里挑的。它是从「**谁在问什么问题、问多频繁、慢了损失多少钱**」里长出来的。
`stages/stage-00.md` 的 T0.3 让你列「问题清单 + 调用频率」,列的就是这张表的左半边。

## 9. 回到 Rung:我们在建什么

```
   ┌──────────────────────────────────────────────────────┐
   │  真实交易所                                            │
   │                                                        │
   │  网关 → 风控 → ▓▓▓ 撮合引擎 ▓▓▓ → 清算 → 行情发布      │
   │                 ↑                                      │
   │                 └── S1 在建的就是这一块                 │
   │                                                        │
   │  S2 rung-feed  → 对应「行情发布」的接收端               │
   │  S3 rung-alpha → 对应做市商/交易者那一侧的信号计算       │
   └──────────────────────────────────────────────────────┘
```

S1 建的是**内核**:那个必须单线程、必须确定、必须极快的部分。
它是整个系统里最小的一块,也是最难写对的一块 —— 因为其余所有部分都可以重试、可以降级,
只有它必须**每一次都对**。

## 10. 术语速查

| 中文 | 英文 | 一句话 |

| 订单簿 | order book / LOB | 所有未成交挂单按价格分档、档内按时间排队 |
| 价格档位 | price level / rung | 同一价格上的所有挂单构成的队列 |
| 最优买价 / 最优卖价 | best bid / best ask | 买盘最高价 / 卖盘最低价 |
| 买卖价差 | spread | best ask − best bid,你的往返交易成本 |
| tick size | — | 最小价格变动单位,价格离散化的依据 |
| 限价单 / 市价单 | limit / market order | 指定价格等待 / 立刻按现价成交 |
| 挂单方 / 吃单方 | maker / taker | 提供流动性 / 消耗流动性。成交价按 maker |
| 价格-时间优先 | price-time priority | 先比价格,同价比先来后到 |
| 排队位置 | queue position | 你在档位队列里的排位,决定成交概率 |
| 库存风险 | inventory risk | 做市商手上货多了,价格反向就亏 |
| 逆向选择 | adverse selection | 和知道得比你多的人成交而受损 |
| 部分成交 | partial fill | 一笔单只成交了一部分 |
| 有效期 | TIF, time in force | GTC 一直有效 / IOC 立即成交否则撤 / FOK 全成否则全撤 / PostOnly 只挂不吃 |
| 自成交 | self-trade | 同一个人的买卖单互相成交,通常必须禁止 |
| AMM | automated market maker | 用公式代替订单簿定价 |
| 流动性提供者 | LP | 把资金存进 AMM 池子赚手续费的人 |
| 滑点 | slippage | 成交量大导致实际成交价变差 |
| 无常损失 | impermanent loss | LP 相对于「单纯持币」的账面损失 |
| LVR | loss-versus-rebalancing | 更严谨的 LP 损失框架;AMM 版的逆向选择 |
| 集中流动性 | concentrated liquidity | LP 指定价格区间,提高资本效率 |
| CLOB | central limit order book | 中央限价订单簿,就是本项目要建的东西 |
